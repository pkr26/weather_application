# Cirrus — Red Re-Audit #3 (2026-09-04, HEAD `85cf97c`)

Method: five parallel adversarial audits with distinct mandates — backend security, backend
logic/resilience, Android data/notify, Android UI/Compose, and contracts + core math + build/CI/docs
honesty — each instructed to *destroy* the code, verify prior-audit fixes, self-vet weak findings,
and cite file:line. The orchestrator then personally re-verified every P1/P2 claim below by reading
the cited lines (marked ✅ where confirmed first-hand).

**Environment caveat (honesty first):** this session had **no JDK and no Node.js runtime** on the
machine, so `:app:compileDebugKotlin`, `:core:test`, `tsc`, and `npm test` were **not executed this
round**. All findings are code-trace verified, not suite-verified. One sub-audit reported
"measured" byte/timing numbers that could not have been produced on this machine; those figures are
downgraded to **analytical estimates** wherever cited below. `backend/.env` exists on disk
(153 bytes), is gitignored, and was never committed (0 entries in history) — keep it that way, and
rotate the key if it was ever pasted anywhere else.

## Verdict

Round 1 found seven P0s. Round 2 found the fix commit didn't compile and its suite was red. Round 3
is the first round where the codebase **held the line**: **no P0s**, and the security core survived
every attack thrown at it — zero auth bypasses, zero identity forgeries, zero prototype-pollution
paths, zero log-injection vectors, timing-safe comparisons everywhere, and all prior headline fixes
verified real at HEAD. What three rounds of escalation have converged on is subtler:

1. **The P0s of round 1 have side doors.** The truncated-forecast fix guards page 0 of pagination —
   a shapeless *later* page (HTTP 200, renamed field, empty list) still ends pagination "healthy"
   and gets cached for the full 10 minutes (P1-1).
2. **The fixes of round 2 introduced races.** The boot-time catch-up machinery now runs
   `REPLACE` against a possibly-*running* briefing worker — the exact worker that cold-started the
   process — and can cancel it into a dead chain that nothing ever revives (P1-2).
3. **The flagship contract is half-built.** The backend's entire `degraded` machinery — the output
   of two audit rounds — is invisible to its only client: the app's `BundleResponse` has no such
   field, and the repository persists degraded bundles as the offline "last known good" (P1-3).

None of these crash anything. All of them silently break a promise the app makes to its user.

## P1 — fix before the next release

### P1-1. A shapeless or empty *later* page (HTTP 200) ends pagination HEALTHY — round-1's
"truncated forecast cached as healthy" P0 re-enters through a side door ✅
`backend/src/upstream/googleWeather.ts:199-207` (guard at `:190` covers page 0 only).

Scenario: page 1 of `forecastHours` returns 24 items + `nextPageToken`. Page 2 returns **200 OK**
with a renamed/absent list key (contract change, error envelope) and no string `nextPageToken`.
Trace: `:199` coerces the non-array to `[]`; `:201` sets `token = undefined`; `:202` breaks;
`:207`'s `token !== undefined && merged.length < target` is false → `truncated = false` → the
24-of-72-hour bundle is served with `degraded: false` and cached at the full 10-minute TTL
(`routes.ts:77-81`). Variant: a *first* page of `{"forecastHours": []}` passes the `Array.isArray`
guard and is served/cached as a healthy 0-hour forecast. The comment at `:177-179` correctly argues
the catch-path re-derives truncation — but the 200-shapeless path has no such guarantee, and
`tests/upstream.test.ts:849-865` pins the wrong behavior ("later page without the list key…
terminates", never asserting `degraded`).

**Fix:** apply the page-0 contract guard to every page — a later page without the list key while
items are still owed must set `truncated = true`; treat a token-less *empty* first page as degraded.

### P1-2. Boot-time `REPLACE` cancels the in-flight briefing worker — and can kill the chain
permanently ✅
`app/.../CirrusApp.kt:27-42` → `NotificationScheduler.kt:81-93` → `scheduleDailyBriefing` default
`ExistingWorkPolicy.REPLACE` (`:57`), invoked at `:92`.

Scenario: briefing posted 08:00; user moves the time to 20:00; process dies. At 20:00 WorkManager
cold-starts the process *for the briefing worker itself*. `Application.onCreate` runs first and
launches `bootReschedule`; `postedRecently` is true (12 h < 20 h window) → `missedToday = false` →
falls through to `scheduleDailyBriefing(..., REPLACE)`. Two orderings, both bad:

- REPLACE lands **mid-`doWork`**: the running worker is cancelled → `CancellationException` rethrown
  (`Workers.kt:173`) → run marked CANCELLED (no retry, no append) → **no pending work remains, so
  nothing ever cold-starts the process again** — notifications are dead until the user opens the app.
- REPLACE lands **before the worker starts**: the pending 20:00 run is discarded and tomorrow's
  scheduled — today's evening briefing silently skipped.

Even the benign morning variant forces the briefing through a duplicate fetch path daily.

**Fix:** before REPLACE, check WorkManager state — if the chain has a RUNNING/ENQUEUED worker for
today, skip (or APPEND_OR_REPLACE); the worker already self-heals.

### P1-3. The app discards the backend's `degraded` flag — and persists degraded bundles as the
offline "last known good" ✅
`app/.../data/remote/dto/Dtos.kt:61-67` (no `degraded` field), `WeatherRepository.kt:38-39`
(unconditional persist), backend emits it at `backend/src/routes.ts:180-184`.

Scenario: upstream truncates → backend serves `degraded: true` → `ignoreUnknownKeys`
(`AppContainer.kt:37`) silently drops the flag → the app renders a healthy-looking short hourly
strip with no stale/degraded banner, and `loadBundle` writes it into `LastKnownWeatherStore` as the
snapshot the offline screen will later present as real. The entire server-side degraded machinery
(two audit rounds of work) is unobservable by its only client.

**Fix:** `val degraded: Boolean = false` on `BundleResponse`; surface it in the stale-banner UI;
skip persisting degraded bundles to the last-known store.

## P2 — real defects, bounded blast radius

1. **All three workers read DataStore outside their try/catch, and the DataStore has no corruption
   handler** ✅ (mechanism) — `Workers.kt:143,146` (`BriefingWorker`), `:215`, `:253` read before
   the `try` at `:159`; `SettingsStore.kt:26` installs no `ReplaceFileCorruptionHandler`. A corrupt
   prefs file → thrown `CorruptionException` → worker FAILURE (not retry) → chain dead; the same
   file crashes the UI on next collect. Trigger is rare (disk corruption/full), impact total.
   *Fix:* move reads inside the guarded region; add a corruption handler.
2. **`DeviceRegistrar` ignores the `storeSecret()` result** ✅ — `DeviceRegistrar.kt:104`. With an
   exhausted keystore vault (`SecretVault.kt:70-71`), every app open ends 401 → `reset()` → new
   record → secret not persisted → repeat: one orphan server-side device record per app open,
   forever. Zero test coverage (the fake always returns true).
   *Fix:* treat `storeSecret == false` as failed registration; surface/log once.
3. **`register()` is not serialized** ✅ (code race; interleaving narrow) — `CirrusApp.kt:43-45`
   (every process start) + `SettingsViewModel.kt:95,102,112` (every toggle) call an unsynchronized
   `register()` (`DeviceRegistrar.kt:56-78`); only id-minting is mutex-guarded
   (`SettingsStore.kt:121-127`). A first-launch + quick-toggle interleaving can leave a mismatched
   id/secret pair → permanent 401 churn. *Fix:* registrar-level `Mutex`.
4. **Any 401 resets the device identity — including API-token 401s no reset can fix** ✅
   (conditional on misconfiguration) — `DeviceRegistrar.kt:61-73`; the token gate
   (`apiToken.ts:32`) and device-secret failures return byte-identical bodies. Backend deployed
   with `API_TOKEN` but APK built without → reset-churn + one orphan record per app open →
   combined with P2-6, eventual `registry_full` 503 for everyone.
   *Fix:* distinguish the two 401 bodies (`invalid_api_token` vs `unauthorized`) or match on the
   device-secret message only.
5. **Geocode routes have no deadline and no client-disconnect abort** ✅ — `routes.ts:204-241`
   (never calls `upstreamScope`, contrast `:168,190,262,297`); `openMeteo.ts:14,34` accept no
   signal. Upstream brownout → each autocomplete tap pins a request for ~24 s (3 × 8 s + backoff)
   and burns fetches for clients who already hung up.
   *Fix:* thread `upstreamScope(svc, req, res)` + signal through both calls.
6. **The device registry is the availability soft underbelly** (paths code-verified; numbers are
   analytical estimates) — unauthenticated registrations (default `API_TOKEN=''`) can fill the
   25 000-record cap → `RegistryFullError` → **503 for every future legitimate device**
   (`routes.ts:353-407`, `deviceStore.ts:188-190`); no eviction route exists (prune happens only at
   load). Every write re-serializes + fsyncs the whole file (~0.5 KB/record pretty-printed →
   ~13 MB per persist near cap). *Fix:* registration requires the token (or per-subnet caps) +
   prune-on-write; move off the single-JSON rewrite (debounce/append-log/SQLite).
7. **The root `AnimatedContent` wipes all weather-screen state on every sheet toggle** ✅ —
   `MainActivity.kt:268-308`. Opening the city list/settings disposes the weather subtree after the
   380 ms transition, so every `rememberSaveable` (hourly expansion `HourlyForecast.kt:124,204`,
   daily expansion `DailyForecast.kt:130`, entrance flags `Enter.kt:48`, list scroll) is discarded —
   scroll snaps to the hero, rows collapse, animations replay. The single most common navigation
   gesture. *Fix:* shared `rememberSaveableStateHolder()` + `SaveableStateProvider(key)` per
   branch.
8. **`playOnce` never replays on key change — the documented city-switch sweep is dead code** ✅ —
   `Enter.kt:49` remembers the `Animatable` **without** the key; on city switch in a surviving
   composition `animateTo(1f)` starts at 1 and completes in one frame. The KDoc (`:31`) and
   `HourlyForecast.kt:119` promise the opposite. Ironically it only fires via P2-7's state wipe —
   the choreography triggers on the wrong event. *Fix:* `remember(effectiveKey)` (or `snapTo(0f)`
   at the top of the effect).
9. **City-list mini-card refresh has no visibility gate** ✅ — `CityListViewModel.kt:89-96`
   refreshes minis on every `cities` emission, and `SettingsStore.kt:59-61` emits on *any* prefs
   write (no `distinctUntilChanged`): overnight during alerts, a `/weather/current` round-trip per
   saved city every ~2 h with the sheet closed and screen off. *Fix:* `distinctUntilChanged()` +
   a STARTED gate (or onResume-scoped collection).

## P3 — tail, grouped

**Backend logic:** core and alerts fetched strictly sequentially per miss — flagship route latency
is the sum of two independent fan-outs while a comment claims parallel (`routes.ts:108-130`,
`googleWeather.ts:321-331`); `LOG_LEVEL` from `.env` is silently ignored (logger reads env before
`loadEnvFile` — ESM import hoisting, `logger.ts:16-24` vs `index.ts:10`); deadline expiry is
reported as 502 with no `Retry-After` (`http.ts:153,161-163` vs `errors.ts:66-89` — should be
504/503+backoff); a 200 with an unparseable body is classified "unreachable" and never retried
(`http.ts:126,163`); unknown future `WeatherCondition` types render as "Cloudy"
(`conditions.ts:69-72`).

**Backend security/posture:** `Cache-Control: public` on token-gated routes lets a shared cache
serve data without the token (`routes.ts:59-67` — briefings correctly use `private`); `gzipSync`
blocks the event loop per ≥1 KB response (`compression.ts:67-84`); no server
headersTimeout/requestTimeout/maxConnections (`index.ts:20-25`); upstream responses buffered with no
byte cap (`http.ts:126`); a store file with `version !== 1` is silently discarded then overwritten —
no quarantine, unlike the corrupt-JSON branch (`deviceStore.ts:92-121`); `API_TOKEN` accepts 1-char
values (`config.ts:86`); `/health` still leaks `process.uptime()` (`routes.ts:143`).

**Android data/notify:** permanent failures retried as transient — a revoked notification
permission or hard 401 burns ~7 briefing fetches/day silently (`Workers.kt:159-177`,
`Notifier.kt:108-118`); `LastKnownWeatherStore.put`'s fallback write is non-atomic and all failures
swallowed (`LastKnownWeatherStore.kt:36-48`); a constraint-starved briefing posts "morning" content
many hours late with no max-lateness guard (`Workers.kt:150-168`); test blind spots exactly at the
new bugs (no `bootReschedule`/`postedRecently`/`missedToday` tests, no `storeSecret=false` test,
no concurrent-register test; DST-gap target 02:30 and month/year rollover unpinned in
`BriefingScheduleTest`).

**Android UI:** `FrameLoop` stale-captures its first `onFrame` — rain drift ignores wind updates
until the effect is rebuilt (`Particles.kt:38-53,83-92`; cosmetic today, the frozen-frame bug class
re-enters the moment loop inputs become dynamic); flat series render degenerate geometry (all-equal
temps → curve pinned to the floor, range bars 2 px — `HourlyForecast.kt:369-370,401`,
`DailyForecast.kt:300,326-331`); per-frame allocations in hot paths (`HourlyForecast.kt:615`
`Path()` per draw, `Particles.kt:106,156,191` color allocs ~4.5 k/s in heavy rain,
`DateTimeFormatter` per row — `DailyForecast.kt:421`, `SettingsScreen.kt:550`); duplicate geocode
results would crash `LazyColumn` keys (`CityListScreen.kt:169` — trigger depends on upstream);
condition→icon/gradient tables can drift (FOG/HAZE/MIST exist only backend-side,
`conditions.ts:27-29` vs `ConditionArchetype.kt`/`WeatherIcons.kt`); offline-hydration path has
zero test coverage (`WeatherViewModelTest.kt:92` constructs the repository without
`LastKnownWeatherStore`).

**Contracts/docs:** on-screen condition text is always English although the app sends its

reasons — `googleWeather.ts:141,231,247,263` vs `MainActivity.kt:147-148`); cleartext claims in
README.md:106/SECURITY.md don't match either network_security_config (release = zero cleartext,

## What withstood the assault (negative results worth recording)

- **Auth core:** 18 path/casing/encoding/duplicate-header tricks against the token gate → all 401;
  timing-safe compares with dummy-hash on unknown devices; device secrets hashed, rotation atomic
  (race-tested), takeover refused; identity entropy 122-bit.
- **Injection/pollution:** `__proto__`/`constructor` at every depth zod-stripped; null-prototype
  store; CRLF in logs impossible (llhttp + pino escaping); no path traversal (deviceId never a path).
- **Briefing integrity:** NaN/±Infinity rejected by `num()`; no division in scoring; invalid
  timezone/date caught; degraded-silence discipline airtight (no "no rain" claim without observed
  data); placeholder parity across all 27 language packs type- and test-enforced.
- **Cache:** single-flight correct (per-flight TTL), LRU-capped, no key collisions, no
  stale-degraded-after-recovery (30 s hard expiry), breaker self-heals via half-open, aborted
  flights never count as failures.
- **Scheduling math:** DST spring-forward/fall-back correct via zoned `Duration` (elapsed-time
  scheduling lands on wall-clock targets); month/year rollover correct; timezone-change handled.
- **Contracts otherwise:** every field name, casing, nullability default, enum value, header name,
  units value, and all 27 language codes line up across the wire; `ignoreUnknownKeys +
  coerceInputValues + explicitNulls=false` makes backend additions safe.
- **Infra honesty (mostly) repaired:** git repo + real remote, pushed, HEAD == origin/main; no
  secrets or build artifacts tracked ever; CI SHA-pinned with scoped permissions; Stryker/PIT/vitest
  gate numbers match their configs; mutation report regenerated the same morning as the fix commit.
